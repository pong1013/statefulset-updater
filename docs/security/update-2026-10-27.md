## Changes

All three application images now use `python:3.13.18-slim-trixie` pinned to the verified multi-platform OCI index `sha256:8a7c3cd378e4e6dfa5d0ea4f6ca1a11068c951e3de3146ebc484eadf4b05a2be`. `requirements.in` records direct dependency inputs and HTTP security floors; `requirements.txt` locks all 27 resolved runtime packages. Kubernetes remains 26.1.0. Flask advances to 3.1.3, requests to 2.34.2, urllib3 to 2.8.0, and Werkzeug to 3.1.9. Dependencies were resolved and installed using real Python 3.13, including wheel availability on arm64.

`requirements-build.txt` separates pip, wheel and packaging installer tools from the application lock. Images use patched pip 26.2.2 during installation, then remove pip, wheel and packaging plus the standard-library ensurepip package and its bundled pip wheel from the final runtime filesystem. Patched setuptools 84.2.1 remains in the runtime lock because Kubernetes 26 explicitly declares it as a dependency; removing it would fail `pip check`.

CI installs the real locked packages on Python 3.13, checks dependency consistency, runs the independent installed-library integration tests with the existing suite, and audits the runtime lock using pip-audit 2.10.1 in a separate environment.

## Residual OS impact and exposure assessment

The 44 HIGH records represent eight distinct CVEs, often repeated across binary packages from the same Debian source package. The remaining MEDIUM, LOW and UNKNOWN findings are retained in the JSON and have not been individually assessed for exploitability. No scanner finding is suppressed. The table distinguishes advisory prerequisites from observed image contents; it is not an exploitability determination.

| HIGH CVE | Potential impact and advisory-specific prerequisites |
| --- | --- |
| [CVE-2026-76642](https://security-tracker.debian.org/tracker/CVE-2026-76642) | util-linux can run privileged post-mount hooks after a mount helper fails, allowing permission changes or inherited SUID filesystem effects. Requires the affected privileged mount/helper/hook path and attacker influence over its inputs/filesystem. |
| [CVE-2026-78408](https://security-tracker.debian.org/tracker/CVE-2026-78408) | A privileged `nsenter --join-cgroup` into an attacker-controlled target can leak a root-opened cgroup descriptor across execution, enabling migration or termination of unrelated host processes. Requires that operator action and relevant namespace/cgroup access. |
| [CVE-2026-78409](https://security-tracker.debian.org/tracker/CVE-2026-78409) | On Linux 6.15 or later, a local user with an fstab-authorized `X-mount.subdir` entry can exploit intermediate symlink traversal to attach an unintended host path. Requires that mount configuration and attacker-controlled path components. |
| [CVE-2026-78410](https://security-tracker.debian.org/tracker/CVE-2026-78410) | A local user able to replace an authorized bind-mount source or writable ancestor can redirect SUID mount to another host directory; configured owner/group/mode hooks can then change that inode with root privileges. Requires the relevant fstab entry and path control. |
| [CVE-2026-54369](https://security-tracker.debian.org/tracker/CVE-2026-54369) | libacl pathname-based ACL calls follow attacker-controlled symlinks. A privileged caller processing such a path can read/change ACLs on an unintended object, permitting local privilege escalation. Merely having the shared library does not establish that caller or input path. |
| [CVE-2025-69720](https://security-tracker.debian.org/tracker/CVE-2025-69720) | `infocmp` has a stack buffer overflow while analyzing crafted terminfo content. Invocation on malicious terminfo can crash the process and presents a potential code-execution concern from memory corruption; code execution in these images has not been demonstrated. Debian describes a CLI crash and links the [upstream fix notes](https://invisible-island.net/ncurses/NEWS.html#index-t20251213). |
| [CVE-2026-16742](https://security-tracker.debian.org/tracker/CVE-2026-16742) | systemd-homed permits local privilege escalation through arbitrary system-group addition for a logged-in homed-managed user. Requires the affected homed service and user-management path; scanner attribution to libsystemd/libudev does not prove that service is running. |
| [CVE-2026-9538](https://security-tracker.debian.org/tracker/CVE-2026-9538) | Perl Archive::Tar before 3.10 can allocate attacker-chosen multi-gigabyte sizes from a crafted tar header, exhausting memory. Requires the module to be available and invoked on the malicious archive. |

Read-only inspection of the final webhook image found `mount`, `umount`, `nsenter`, `tic`, `infocmp` and `perl`; mount and umount have SUID mode bits. `setfacl`, `getfacl` and `systemd-homed` were not found in PATH, and neither `/usr/lib/systemd/systemd-homed` nor `/lib/systemd/systemd-homed` existed. `perl -MArchive::Tar -e 1` failed to load Archive::Tar from that image's configured module search path. Its `/etc/fstab` contained only the unconfigured-base-system comment. These bounded checks do not prove absence from every possible path or deployed volume, nor do they remove the source-package findings. All three images share the scanned OS package set, but this executable/path inspection was performed on the final webhook image only.

Dockerfiles invoke the Python application directly and specify no `USER`; inspection showed an empty image User setting and `uid=0(root)` under ordinary Docker execution. All three chart defaults set pod/container security contexts to `{}`: they do not explicitly enforce a non-root UID, capability dropping or `allowPrivilegeEscalation: false`. Actual Kubernetes admission policies, capabilities, seccomp profiles, kernel version, host mounts, namespace sharing and deployed values were not inspected. Root inside a container and SUID mode bits alone do not establish host privilege or that these exploits work, but they prevent assuming protective deployment restrictions.

The webhook accepts HTTPS HTTP admission requests at `/mutating` on port 443. The operators consume Kubernetes events and API objects; automatic resizing additionally runs shell/df commands through the Kubernetes exec API **inside the selected workload pod**, not as a local mount/archive/terminfo operation. Reading the three entry points found no direct invocation of the affected local mount/nsenter, ACL, infocmp, homed or Perl archive paths. This limits the observed intended call paths; it does not establish absence of an indirect dependency path, malicious filesystem/terminfo/archive input, compromised-process path or administrative use. Network reachability alone does not demonstrate the advisory-specific local prerequisites, and package presence alone does not demonstrate exploitability.

**Per-CVE exploitability remains unassessed, and overall release risk remains unknown pending review of the actual deployed configuration and workload trust boundaries.** The OS vulnerabilities are not eliminated by the Python update and are not automatically exploitable because the scanner reports them. Continue monitoring Debian/base-image updates and rebuild/re-scan when fixes become available. Deployment review should evaluate non-root execution, privilege escalation restrictions, reduced capabilities and host/volume exposure against operational needs; changing those settings is outside this update. These findings and the missing live-cluster verification remain release limitations, not an approval to deploy.
